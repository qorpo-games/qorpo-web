AI-assisted Unreal DataTable code: test the missing row

Q
QORPO Studio25 November 2026 · 4 min read

Review AI-assisted Unreal DataTable code with a missing row as well as a valid one. Confirm both the table and the row name, then decide what the feature should do when that lookup cannot supply the expected data. A valid table pointer alone does not describe the whole lookup.

The example below is a proposed review fixture for a small item-information panel. It is not an account of a failure in a released QORPO game, and no Unreal test run is claimed.

Name the data contract

Use a model panel that reads an item name, icon and description from one table row. Write down the intended row and the required fields before asking an assistant to change the lookup.

Then define the missing-data result. The panel might show an explicit unavailable state, omit a nonessential detail or stop an action that requires valid data. The correct choice depends on the feature. Silently displaying another item's information would usually answer the wrong question even if the panel looks complete.

Keep that design decision in the review. An assistant cannot choose a meaningful fallback merely by ensuring the graph does not stop.

Inspect table and row together

Epic's FDataTableRowHandle reference describes a handle with a DataTable field and a RowName field. Those two pieces identify the intended row relationship.

For the model fixture, record both. Two tables can use a similar row name while containing different information. Conversely, the right table can still be paired with the wrong row name.

Ask the assistant to point to the source of each value. If one comes from an exposed property and another is assembled from display text, that deserves a specific explanation. A player's translated label is not automatically an appropriate stable identifier for data lookup.

Test a valid result first

Start with a known row and confirm the panel reads the expected fields. Do not stop at the item name if the feature also depends on the icon or another required value.

Keep the fixture small enough that the expected result can be checked without guessing. Use a deliberately distinctive model item so an accidental fallback to a neighbouring row is visible.

This establishes the comparison point. It does not validate every row in the production table, but it makes the later missing-row case easier to interpret.

Remove the expected row from the fixture

In an isolated test copy, give the panel a row name that the chosen table does not contain. Observe the lookup outcome and the panel's response. The review should confirm that the implementation follows the fallback rule written earlier.

Do not change shared production content just to make this case fail. A controlled fixture can exercise the error path without disrupting other features that use the same table.

Record what actually happened when the case is executed. This article proposes the sequence; it does not present the missing-row outcome as a passed automated test.

Keep empty and missing different

A row can exist while a particular optional field is empty. That is a different condition from the row not being found at all. Decide which fields are required and which may be omitted.

For the model item panel, an absent optional description might allow the rest of the panel to remain useful. An absent identifier needed to perform a purchase or equip action could require a different response. Those examples are design possibilities, not claims about a QORPO purchase flow.

The review should therefore distinguish lookup failure from field validation. A single generic “valid data” branch can hide that distinction.

Recheck after data changes

If a workflow includes table reimport or row changes, include the relevant refresh path in the fixture. Reopen or refresh the panel through the supported flow and verify the new expected content.

Do not assume that a screenshot taken before a data edit proves the display after the edit. If the implementation caches anything, ask the assistant to explain the cache's lifetime and invalidation rule.

Epic's data-driven gameplay documentation explains the table and row-name relationship and cautions about keeping retrieved data valid when tables refresh. Use the documentation appropriate to the project's engine version when implementing a concrete solution.

Review the player's message

A useful unavailable state should explain what the player can do next without exposing internal table paths or debug identifiers. Keep detailed diagnostics in an appropriate development record.

If the panel has a retry or refresh action, test that action separately. A visible fallback is only the beginning if the normal user flow offers a way to recover.

Our AI code review guide gives a broader acceptance structure. The expected-result fixture guide helps make the fallback precise before implementation.

What to save with the change

Keep the intended table, row name, required fields, fallback rule and executed cases together. Include wrong-table, missing-row and empty-optional-field cases when they are relevant.

For assets referenced by a row, our asset-loading guide addresses the separate loading moment. Follow QORPO development for studio progress. The goal here is a reviewable data contract rather than a happy-path screenshot standing in for every lookup.

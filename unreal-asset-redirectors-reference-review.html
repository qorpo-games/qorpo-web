Unreal asset redirectors: check the references after the move

Q
QORPO Studio24 November 2026 · 5 min read

After moving or renaming an Unreal asset, check the content that refers to it before treating the old location as disposable. Unreal asset redirectors allow references at an old location to reach the new asset. Fixing them involves saving the referring packages, so a clean-looking folder is not the same thing as a verified move.

The workflow here is an original review example for a small asset move. It is not a report that a particular QORPO project has lost references, nor a claim that a packaged build was tested.

Give the move a narrow scope

Choose one asset and list the known places that use it. In a model exercise, move a material used by a placed prop and a Blueprint. Record the old and new paths before changing anything.

Use the editor's asset operations rather than reorganising binary project files as if they were unrelated documents. Keep the move small enough that the resulting source-control changes can be reviewed.

This preparation also defines the acceptance boundary. A reviewer can check those dependent objects deliberately instead of opening the project, seeing no obvious error and assuming every reference survived.

Understand the redirector's purpose

Epic's asset redirector documentation explains that an asset move or rename leaves a redirector at the old location. Packages that are not loaded can still find the asset through that route.

The redirector is therefore evidence of a relationship being preserved. Its presence is not, by itself, proof that a move failed. Its disappearance is not, by itself, proof that every dependency now points directly to the new location.

Keep the old and new names in the review record. When a warning refers to the old path, those details help identify whether the remaining work concerns a known move or an unrelated missing asset.

Inspect the referencers

Use the available reference tools to identify which assets point to the moved content. Epic's Reference Viewer guide describes a graph for viewing asset relationships.

For the model material, inspect the known prop and Blueprint, then consider whether the graph reveals another dependency that belongs in the check. A folder-based assumption can miss content stored elsewhere in the project.

Do not interpret a reference graph as proof that every runtime loading path has been exercised. A project may also use paths in configuration or other logic. Keep those project-specific uses in scope when they exist.

Fix deliberately, then review what was saved

The documented editor fixup operation attempts to resave packages that point to the redirector and removes it when the required referencers can be resaved. That means the operation can affect more files than the moved asset alone.

Before accepting the change, inspect the source-control list. Confirm that the expected asset move and dependent package updates are present. Unexpectedly broad changes deserve investigation rather than automatic acceptance because the folder now looks tidy.

If a package could not be saved, resolve that concrete obstacle. Do not replace the explanation with manual deletion of the old file. Removing a reference route is not a substitute for updating the content that relies on it.

Reopen the dependent content

Open the model prop's level and the Blueprint that used the material. Inspect the intended material assignment and the visible result. Save, close and reopen the relevant content as separate steps if the review requires persistence.

Then test the path that matters for the feature. If the asset is loaded on demand, exercise that moment instead of checking only an already-open editor preview. Our asset-loading guide explains why a resource being visible in one state does not validate every later loading path.

Record actual outcomes. A proposed sequence is useful preparation, but it should not be described as passing until somebody runs it.

Keep asset and code redirects distinct

An asset redirector left by moving a content asset is not the same mechanism as a Core Redirect for a renamed class or property. Epic's Core Redirects reference describes remapping reflected names during loading.

If the change also renames a code member, investigate that migration separately. Do not expect fixing content redirectors to solve every serialized-name change.

The distinction matters in review descriptions. “Moved this material and fixed its asset referencers” is more precise than “fixed all redirects”, especially when an unrelated code refactor is happening nearby.

Use automation within an understood boundary

Epic also documents commandlet-based redirector cleanup. For a large project, that can be useful, but it does not remove the need to understand which files will change or how the result will be validated.

Prove the small workflow first, then choose the scope of automation appropriate to the repository and source-control setup. Review logs and the changed packages. Avoid mixing a sweeping cleanup with unrelated art edits if that makes the move difficult to assess.

Our visual bug capture guide can help document a wrong material or missing resource before and after the change.

What a useful completion claim looks like

State the moved asset, the dependent content checked, the saved-package review and any executed loading or build checks. List the remaining paths if they were not tested.

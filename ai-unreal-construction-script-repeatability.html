AI-assisted Unreal Construction Scripts: review the second rebuild

Q
QORPO Studio24 November 2026 · 5 min read

Review an AI-assisted Unreal Construction Script by repeating the edit that produced the first attractive result. A useful editor tool should return a predictable configuration when its inputs return to the same values. The second rebuild, a reduced count and a duplicated actor can reveal assumptions that a single screenshot cannot.

The railing example below is an original review fixture. It is not a report of a released QORPO gameplay feature, and no Unreal test run or performance saving is claimed.

Define a result that can be counted

Use a small railing Blueprint with an exposed post count and spacing value. For the model fixture, four posts at the chosen spacing should produce one four-post arrangement owned by that actor.

Write that expectation before reviewing the generated graph. Include what a count of one should mean and what the tool should do with values outside the accepted range. An assistant cannot choose a correct boundary behavior when the design leaves it undefined.

Keep the visible result simple. A complex procedural street may look impressive while making it hard to identify which part came from the most recent edit. Four posts are easier to inspect and compare.

Understand why the editor path matters

Epic's Blueprint Foundations describes Construction Script execution when an actor is created and when an editor transform or property changes. It is an initialization and configuration path, not simply an action that runs once after the player presses a button.

That makes repeatability relevant. A change that looks correct after placing the actor may behave differently after adjusting its properties, moving it or compiling its Blueprint.

Do not infer a bug merely because construction runs again. Review whether the script's intended result survives the supported editor operations. The requirement concerns the resulting configuration, not preventing Unreal from doing normal editor work.

Inspect what the script owns

Ask which components or other objects the implementation creates, modifies or references. Separate generated content from authored content that the artist placed deliberately.

A broad cleanup that removes everything of a particular type can be as problematic as a script that leaves unwanted output behind. It may erase a hand-authored attachment or modify another actor. The review should establish the narrow ownership boundary before accepting a cleanup step proposed by AI.

Epic's construction rerun API documents rebuilding autogenerated components. Do not generalise from that behavior to every custom object, external reference or side effect an implementation might introduce.

Change the count in both directions

For the model fixture, move from four posts to six, then from six to two, then back to four. At each step, count the intended visible posts and inspect the relevant hierarchy or instance data for the implementation you are reviewing.

Growing a result is only one direction. Reducing it tests whether an earlier, larger configuration still influences the output. Returning to the starting value tests whether the tool can recreate the same arrangement rather than accumulating history.

These are proposed steps. A reviewer should record actual counts and observations when running them in the project. This article does not present hypothetical output as a passed test.

Move, duplicate and change one instance

Next, move the model actor, then duplicate it and change only the duplicate's spacing. The original should retain its intended configuration if the tool is designed for independent per-instance editing.

If both instances change, investigate whether they share a mutable asset or another state source that the author did not intend to share. Do not immediately add another reset node without identifying what is shared.

Our material-instance review explores a related ownership question. The AI code review checklist gives a broader structure for explaining a generated implementation before accepting it.

Include undo and a reopened level

If the editor tool is expected to support ordinary undo, include a property change followed by undo in the review. Check both the displayed property and the resulting arrangement. A value returning to four is not enough if the visible output remains in a six-post state.

Save and reopen the test level as a separate case. Record the engine version and whether the actor was placed in the level or spawned for a runtime test. Do not assume that one path proves the other.

The aim is a small, repeatable evidence set. It is not a claim that every editor operation or packaged-build behavior has been covered.

Review responsiveness separately

A Construction Script can be visually correct while making an editor action awkward. Try the operation at a representative scale only after the small fixture is understandable.

If dragging or editing becomes slow, measure the specific operation and inspect what work it triggers. Do not claim that AI reduced construction time without a baseline and an actual measurement. Conversely, a fast four-post fixture says little about thousands of generated objects.

Keep this distinct from game frame-rate testing. Editor responsiveness and a player's runtime frame rate answer different questions.

Record the acceptance boundary

A useful review record includes the input values, expected count and spacing, ownership rule, executed editor operations and any untested paths. Ask the assistant to describe how its graph handles shrinking, rebuilding and per-instance changes.

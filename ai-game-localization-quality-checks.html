AI game localization: what to check before a translation ships

Q
QORPO Studio21 October 2026 · 7 min read

An AI translation is ready for a game only when its meaning, terminology, variables and on-screen behaviour survive review in context. Fluent sentences are an input to that process, not proof of completion. Use AI to help prepare and inspect text, then make a human reviewer responsible for the player-facing result.

This is a practical production workflow, not a claim about measured QORPO translation savings or a particular model winning every language pair. It builds on the distinction in reviewing AI-generated game code: generated output still needs an explicit acceptance standard. Translation has a different standard because tone, context and interface behaviour all matter.

Why a natural sentence can still be wrong

A short game string rarely contains enough information to translate itself. The word Charge could describe a combat action, an electrical state or a payment. A translator who sees the screen and the player action can distinguish them. A model given a disconnected spreadsheet row has less context, even if its answer sounds convincing.

The resulting error is not always a bad sentence. It can be an instruction that sends the player towards the wrong action. It can also be a new name for an item the game has already introduced under another name. Both problems survive a review that asks only whether the target language is fluent.

Build a small context record around ambiguous strings. Include the screen, who is speaking, what action follows and whether the text is a label, instruction or dialogue line. The goal is not to send a model the whole project. It is to supply the information needed for a specific decision while keeping unreleased story material and private data out of unnecessary tools.

Start with a glossary that can resolve a disagreement

A useful glossary does more than collect words. It records the approved term, meaning and exceptions. If a creature name must remain unchanged, say so. If a verb should differ between a friendly prompt and a technical menu, describe that difference. A bare list cannot explain why two translations disagree.

Consider a model example. A fictional item called a Spark Seed appears in inventory, a recipe and a quest. Translating those three appearances separately may produce three plausible names. The player then has to infer that they are one object. A glossary entry prevents the problem by connecting the term to its role and preserving the same choice across contexts.

Keep unresolved terms visible. Marking a decision as pending is better than allowing an early generated suggestion to become the standard by accident. Give the decision an owner and record the reason once, so every reviewer does not repeat the same argument.

Protect variables and formatting before reviewing style

Treat placeholders as part of the interface contract. In a model string such as Collect {count} seeds, the variable name is not prose. A translator may need to change word order, but should not rename the identifier or accidentally turn it into a fixed number.

Automated checks can compare placeholder sets, detect missing markup and flag strings that became empty. They can also identify a suspicious length increase for review. These checks are useful precisely because they do not require a model to judge whether the sentence feels natural.

Passing them does not establish linguistic quality. A string can preserve every variable while saying the opposite of the source. Keep mechanical validation and language review as separate gates, with separate reasons for failure. That makes a later correction easier to understand and reduces the temptation to treat one green indicator as approval of everything.

Use AI as a second reader, with a limited question

Instead of asking a model whether a translation is good, ask a narrower question. Does the target preserve the speaker's intent? Are glossary terms consistent? Does it introduce a promise the source does not make? Is a negation missing? Each question produces a reviewable observation rather than a vague score.

Do not let the same model's confidence substitute for independent judgement. A generated explanation can sound authoritative while defending the original mistake. Have the reviewer inspect the source, target and context directly. If the issue affects a purchase, accessibility instruction or irreversible action, the acceptance decision needs particular care.

Research also treats this as an evaluation problem rather than a solved convenience feature. The paper Benchmarking Large Language Models for Game Localization Quality Assurance studies LLM-based game localization QA across models and languages. Its existence supports testing the evaluator itself. It does not justify assuming that a model's judgement transfers unchanged to every project or language.

Test the string where the player encounters it

Put reviewed text back into the interface before calling it finished. Check whether the button still fits, whether the line break separates an instruction awkwardly and whether a controller prompt makes sense on the intended platform. A screenshot can reveal an issue a text-only review cannot see.

A useful test sequence contains a narrow screen, a larger text setting and the most demanding supported script for the selected font. Check the actual fallback glyphs, not just a font's advertised language coverage. Pay attention to menus that place an icon beside a sentence or reserve a fixed width for a number.

Use representative navigation to reach the string. Opening an isolated widget does not prove that the right text appears after a failed action, a return to the menu or a language change. Localization QA is partly state QA: the wording must be correct in the state where the player reads it.

Separate harmless awkwardness from a blocked task

Prioritise issues by their effect. A slightly flat line of optional dialogue and an incorrect instruction for confirming a purchase should not share the same release priority. A missing character that turns an item name into boxes can block understanding even when the underlying translation is correct.

Record the issue, affected language, screen and consequence. Include the proposed correction and the person who approved it. This turns feedback into a change the team can reproduce rather than a debate about taste. Where a choice is stylistic, say so; where it changes meaning, explain the difference.

Avoid a single quality percentage without an interpretable denominator. Ten issues in ten thousand optional lines mean something different from one blocker in the first onboarding screen. Report what was reviewed and what remains outside the sample. That is more honest and more useful for a release decision.

Keep a small regression set

Save examples that have failed before: an ambiguous combat verb, a plural-sensitive sentence, a long button, a dialogue line with a character name and a message containing multiple variables. Re-run them when the glossary, prompt, model or interface changes.

The set should contain actual failure modes, not only easy sentences selected to demonstrate success. A new workflow that improves a general sample may still break the one phrase that repeatedly confuses players. Review that phrase directly rather than hiding it inside an average.

This is also where human effort becomes more focused. Mechanical checks catch repeated technical mistakes, a model can help surface candidates, and reviewers spend time on context and judgement. That is a workflow hypothesis to measure, not a guaranteed cost reduction. Track review time and escaped issues together before deciding whether the process is more efficient.

A compact release handoff

The handoff should identify the text revision, glossary revision, reviewed languages and tested builds. State who accepted linguistic changes and which screens were inspected. Attach unresolved issues with their user impact. A confident summary is less valuable than a record another person can follow.

For game teams working across products, this discipline protects brand consistency without forcing every product to sound the same. A family story and a combat menu can share a studio while needing different voices. Our TAMITOS localization case study examines the related question of different audiences and local service scope.

Continue with prototype and release evidence for the wider acceptance process, or explore QORPO's studio approach. AI is useful when it makes a responsible production process easier to execute. It should not make responsibility harder to locate.

Questions teams often ask

Can a second AI model approve the first model's translation?

It can provide another review signal. Approval still needs a defined standard and a responsible reviewer, particularly where context, safety, commerce or accessibility affects the meaning of the text.

Is a character limit enough to prevent layout issues?

No. Width depends on glyphs, font, size and layout. Test representative strings in the actual interface and supported settings rather than treating character count as a visual measurement.

Should every string go through the same review?

Use the same accountability, but vary the depth by risk and context. First-run instructions, account actions and purchase wording deserve different attention from optional flavour text. Record the coverage so the difference is explicit.

Unreal UMG DPI scaling: inspect the menu at the size players use

Q
QORPO Studio25 November 2026 · 4 min read

Check a UMG menu at the viewport sizes players will actually use, and record the DPI scale being applied. A layout that fits one editor preview can still produce cramped labels, weak focus visibility or controls that are difficult to use at another size. DPI scaling is one part of that review, not a substitute for it.

The procedure below is an original menu-review fixture. It is not a claim that a particular QORPO game has passed a device audit or that a scaling change improved performance.

Start with the menu's real task

Choose a small menu with a concrete action: select an item, read a short explanation and confirm or cancel. Include the longest realistic label and an unavailable state in the fixture.

Those states matter because an empty menu or a row of short placeholder words is an easy case. The difficult case may appear only when a translated label wraps or a warning shares space with a button.

Write down the viewport dimensions used for the first comparison. A screenshot without those dimensions makes it harder to understand whether the difference came from content, layout or scale.

Record the scaling settings

Epic's DPI Scaling documentation describes the User Interface project's application scale, DPI scale rule and curve. The chosen rule determines which viewport dimension drives the curve.

Keep those values with the fixture rather than assuming all projects use the same defaults. A comparison is more useful when another reviewer can reproduce the same scale decision.

Do not adjust the curve solely to make one screenshot look comfortable. Check the intended range of viewports before accepting a global change that affects other menus too.

Separate UI scale from scene resolution

A game can change how its three-dimensional scene is rendered while presenting its user interface through a different part of the pipeline. Do not use a scene-resolution percentage as a shorthand for the menu's DPI scale.

For this fixture, record both the viewport dimensions and the actual UI scaling information. If a separate rendering comparison is also needed, keep it as a different case.

Our render-resolution comparison guide covers that wider performance question. This article concerns whether the menu remains readable and usable when its layout is scaled.

Compare a small set of meaningful sizes

Choose the sizes and aspect ratios relevant to the product instead of collecting many arbitrary screenshots. For a model PC menu, compare a smaller window with the intended full-screen presentation and a wider aspect ratio if that is supported.

At each size, perform the same task. Read the explanation, move focus to the intended control and confirm or cancel. Check that information is available without requiring a reviewer to remember what was visible in another configuration.

These are proposed cases. Record the actual outcome when somebody executes them in the project. No menu interaction was tested in Unreal for this article.

Check the edges and the middle

Inspect content near the viewport edges as well as the central panel. A correctly sized centre panel does not prove that an anchored prompt or corner control remains in a useful place.

Epic's UI scaling guide discusses adapting UI across device sizes and points to anchoring when widgets shift out of view. Use the layout tools appropriate to the menu rather than compensating for every placement problem with a single scale value.

Also check wrapped text. A label can remain technically inside its box while pushing a second control out of the useful reading order.

Focus needs to survive the comparison

A menu is not complete when the labels are visible but keyboard focus is hard to identify. Follow the same navigation sequence at each size and look for a clear indication of the active control.

If a dialog opens, test closing it and returning to the intended menu state. Our focus-return review addresses that transition.

Keep visual inspection and input testing together. Scaling can change the spacing and apparent grouping of controls, which affects whether the next action is understandable even when the underlying input mapping remains the same.

Inspect text in the actual viewing context

A large capture viewed on a small laptop is not the same thing as the game running at the target size. Review the menu in its intended presentation and, where relevant, at a normal viewing distance.

Do not turn a font-size value into a universal accessibility claim. Legibility also depends on contrast, font design, content length and the person's needs. Use appropriate user and assistive-technology testing when the claim requires it.

For a practical record, note which labels were difficult to read, where wrapping occurred and which action became ambiguous. Those observations are more useful than simply writing “UI too small”.

Keep the acceptance claim specific

Save the viewport sizes, scale settings, tested content states and input sequence. State what was observed and which configurations remain untested.

The input accessibility review provides a wider action-based checklist. Follow QORPO's studio work for product updates. A good scaling review ties a visible layout decision to a task somebody needs to complete.
